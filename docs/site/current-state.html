How combo discovery works today

The system searches the space of Magic: The Gathering card interactions for loops that produce unbounded value, verifies them inside the actual rules engine (Forge), and measures the result against the community's known-combo database (Commander Spellbook). It is two halves: a headless rules oracle, and a symbolic/statistical science layer on top of it.

00

Two halves

Everything below is one of these two layers, or the boundary between them.

Oracle · Java

Forge harness

Runs legal games headlessly, exposes typed decisions, Snapshot/Restore, and deterministic scenario injection. It is the only thing that can certify that a loop actually happens.

Science · Python

Corpus to candidates

Imports the card corpus and ground truth, builds the predicate ontology and interaction algebra, evaluates proposals, analyses motifs, runs combo testing, and presents results in the review TUI.

01

Master pipeline

Eight stages, each labelled with what it consumes, what it produces, and the command that runs it. Every stage reads from and writes to the same append-only store.

02

The gRPC boundary

A Python process drives a Java rules engine over gRPC. Everything the science layer can do to a game crosses this boundary and nothing else.

03

Combo testing inner loop

This is the part that turns a hypothesis into an engine-backed answer. A candidate pair is injected into a live game, driven with a choice-aware policy, and watched for structural recurrence plus growth.

04

Store map

One database. 31 tables plus schema_version, grouped by what they are for. Nothing is ever updated or deleted.

Motif enrichment

Known pairs are strongly predicted by motifs: the copy/untap motif shows a lift of 328, cross-motifs range from 18 to 1094, with p ≈ 0. Crucially, false positives are also enriched. The problem is therefore the composition rules that combine motifs, not the motif vocabulary itself.

06

What does not work yet

Stated plainly, because a Loop Detector you cannot trust is worse than no Loop Detector.

  1. Loop Detector false positives (open)

    Kiki-Jiki + Keldon Overseer and Kiki-Jiki + Elven Raft-Steerer are reported loops but cannot legitimately loop. Scenario injection places the card without casting it, so cast-conditional (Card.Self + kicked) and landfall triggers fire wrongly.

    live diagnosis: link_hits=[0, 4] — the untap link never executed, yet state recurred and a traced resource grew. Until fixed, loops verdicts for cast-conditional or landfall cards are unverified.

  2. Tier-B second source is empty

    The system never reports "novel" — only candidate or needs_second_source. Commander Spellbook alone is not sufficient, and EDHREC would not count because it is Spellbook-powered.

  3. The candidate pool is stale

    It predates the Un-set / legality exclusion fix, so rows such as eager beaver + … remain. The pool must be rebuilt.

  4. No scale run yet

    Only a small discovery batch has been executed. Two Test Runs are persisted in this database.

  5. Engine limits

    Snapshots cap at 32 live tokens; one game per process; FullState is partial.

07

Reproduce

The pipeline in its real order. Each command is independent and idempotent against the append-only store.

Pipeline

  1. uv sync
  2. bash scripts/gen_stubs.sh
  3. Boot the harness: 
    $ java -Djava.awt.headless=true -jar forge-harness-*.jar \
    --port 50051 --assets <forge/forge-gui-desktop>
  4. uv run combo-import-cards
  5. uv run combo-import-spellbook --download
  6. uv run combo-build-ontology
  7. uv run combo-evaluate
  8. uv run combo-analyze-motifs
  9. uv run combo-witness --candidate <id> --persist
  10. uv run combo-tui

Gates

$ uv run pytest
$ bash scripts/check.sh
$ uv run python scripts/compare_algebra.py --db research.db --top 10
